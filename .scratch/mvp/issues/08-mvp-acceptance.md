# 08 — 完整故障验收与长任务演示

**What to build:** 项目使用者能够从干净的开发环境运行整个 MVP，并查看可复现证据，确认崩溃接管、幂等重试、取消、超时、审批和调度能共同工作。

**Blocked by:** 03 — 外部工具调用的幂等恢复；06 — 指定步骤的人工审批与恢复；07 — 一次性定时执行

**Status:** ready-for-agent

- [ ] 将 spec 的全部验收组及设计故障矩阵映射到已有测试/证据，补齐跨功能组合缺口；不得将前置票必须完成的单功能测试留到此票才首次实现。
- [ ] 运行真实 PostgreSQL 与编译后的独立 API、Worker、Scheduler；自动故障测试覆盖原子性、提交响应丢失、租约过期前后、预算耗尽、容量、数据库不可用、终态竞争及恢复。
- [ ] 验证重试任务进入审批再恢复、审批中取消/超时、定时任务取消，以及幂等工具在崩溃接管后的组合行为；数据库、事件与副作用断言一致。
- [ ] 完成约 30 分钟的进程级演示：至少两个 Worker、一次执行中崩溃和接管、人工批准、一次业务失败重试，最终 SUCCEEDED，已成功提交 Step 重跑数为 0。
- [ ] 演示配置使 Task deadline 足够覆盖实际演示及审批等待；记录真实耗时，不用缩短测试时钟声称完成长任务演示。
- [ ] 记录可复现启动/测试/故障注入步骤、配置与版本、数据库断言、工具副作用计数、结果和限制；未运行或受环境阻碍的场景明确未通过，不以日志或 fixture 冒充真实进程证据。
- [ ] 开发数据库普通停止/启动和保留卷重建后数据保留；测试清理不影响开发/演示数据；显式重置仅作用于指定目标。
- [ ] 提供使用和可靠性说明：固定 Workflow、总超时起点、重试预算、审批身份、取消响应含义、执行器兼容要求；明确非幂等副作用和不协作工具的边界。
- [ ] 执行适合 Go 项目的格式、静态检查、单元/集成测试及有意义的并发竞态检查，记录实际命令和结果；最终仓库验收不新增 spec 之外的产品能力。
